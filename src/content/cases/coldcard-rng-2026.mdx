In late July 2026, bitcoin self-custody users of **COLDCARD** hardware wallets
(made by **Coinkite**) faced an active theft wave tied not to a consensus bug,
but to **weak wallet seeds** produced by affected firmware — seeds that could
be reconstructed **offline** without physical access to the device.

## What the public record establishes

### Scope and risk conditions (Coinkite)

According to Coinkite’s security advisory (30 Jul 2026, updated 1 Aug 2026):

- **Mk2/Mk3 firmware 4.0.1–4.1.9**: funds controlled by device-generated seeds
  are at risk if created **without** ≥**50** fair independent private dice rolls
  **and** without a **strong, unique BIP-39 passphrase**.
- **Mk4, Q, Mk5** seeds generated before fixed releases: also affected
  (Coinkite: ~**72 bits** vs expected **128**).
- **Dice exception:** ≥50 independent private dice rolls mixed into seed
  creation (per Coinkite’s documented path) are treated as restoring adequate
  entropy for this issue alone.
- **Passphrase:** a strong unique BIP-39 passphrase is an independent barrier
  but does **not** repair a weak seed; Coinkite still recommends migration.
- **Not affected:** TAPSIGNER, OPENDIME, SATSCARD (different codebases).
- **Fix ≠ repair:** fixed firmware (Mk2/Mk3 **4.2.0+**; Mk4/Mk5 std **5.6.0+** /
  Edge **6.6.0X+**; Q std **1.5.0Q+** / Edge **6.6.0QX+**) corrects *new* seed
  generation only. Existing weak seeds must be **replaced** and funds migrated.

### Thefts

On-chain sweeps of many addresses believed linked to weak Coldcard-generated
wallets were reported from **30 July 2026**. Media and research trackers
published evolving BTC totals (hundreds to 1,000+ BTC in early estimates).
**Coinkite’s primary advisories do not publish an official stolen-funds total**;
this archive does not freeze a single USD/BTC loss figure as a vendor fact.

No public LE charging document against a named thief is cited here. Legal
status: **unresolved**. Case status: **open**.

## Technical analysis

Synthesized from Coinkite’s entropy deep dive and Block’s engineering report
(both primary technical sources). Block notes its analysis is based on source
review and was published during active exploitation; full empirical exploit
benchmarks are not claimed.

### Root cause chain

1. **Board config disables MicroPython’s HW-RNG build**  
   Production headers set `MICROPY_HW_ENABLE_RNG` to **0** because COLDCARD
   supplies its own STM32 RNG wrapper (`ckcc.rng_bytes` / board `rng.c`).

2. **libngu checks the wrong condition**  
   libngu uses `#ifndef MICROPY_HW_ENABLE_RNG` (macro *defined*?) rather than
   testing a non-zero *value*. With the macro defined as zero, the build still
   “succeeds” and libngu binds `CHIP_TRNG_32()` to MicroPython’s `rng_get()`.

3. **MicroPython compiles the software fallback**  
   With `MICROPY_HW_ENABLE_RNG == 0`, `rng_get()` is the **Yasmarang** software
   PRNG, initialized from **UID low 32 bits**, **SysTick**, and **RTC**
   registers — fixed identity and timing state, not a cryptographic TRNG.

4. **Wallet generation switched path (March 2021)**  
   Pre-v4: `rng_bytes(seed)` → hardware path.  
   Commit `b18723dd` (1 Mar 2021) → `random.bytes(32)` → `ngu.random.bytes`.  
   That path no longer hits the intended TRNG for seeds.

5. **XOR with a second Yasmarang does not add entropy**  
   libngu XORs the fallback stream with another Yasmarang state seeded from
   public constants. XOR of two reproducible streams is reproducible.

6. **Mk4+ “reseed” is only 32 bits**  
   Boot reads SE1/SE2 material, hashes it, and passes **four bytes** into
   `reseed()`, which replaces a **single** 32-bit Yasmarang word. Block:
   for fixed fallback state and call history, ≤ **2^32** securely distinguished
   output streams (~**2^31** average enumeration). SHA256d of the 32-byte
   output **cannot** increase the number of possible seeds.

### Device impact (Block assessment summary)

| Device / firmware when secret was generated | Assessment (Block) |
| ------------------------------------------- | ------------------ |
| Mk1 (all through v3.0.6) | Outside this regression |
| Mk2/Mk3 through v3.2.2 | Direct STM32 hardware RNG |
| Mk2/Mk3 **v4.0.0–v4.1.9** | Confirmed vulnerable path; no secure reseed |
| Mk4 production v5.0.0+ (pre-fix) | Fallback remains; reseed limited to 32 bits |
| Q / Mk5 production (pre-fix) | Same construction as current Mk4 path |

**Exposure depends on the firmware used when the secret was generated**, not
the manufacturing date of the plastic. Upgrading firmware does not change an
old seed.

### Entropy / search-space estimates (as stated by sources)

| Source | Model | Stated scale |
| ------ | ----- | ------------ |
| Coinkite (preliminary) | Mk2/Mk3 affected | ~**40 bits** effective search space |
| Coinkite | Mk4/Q/Mk5 pre-fix | ~**72 bits** vs **128** expected |
| Block | Mk2/Mk3 v4, known UID + timers + history | deterministic (`2^0`) under strong attacker knowledge; broader ceilings if timers unknown |
| Block | Mk4/Q/Mk5 successful reseed, fixed fallback | ≤ **2^32** streams |

These are **attack-model estimates**, not proofs that every wallet is free to
steal for every attacker. Practical cost depends on UID knowledge, boot timing,
RNG call history, and derivation work.

### Attack surface (how theft works)

1. Attacker constrains or recovers enough of the deterministic RNG state (and,
   for later devices, enumerates the 32-bit reseed where applicable).
2. Candidate seeds/keys are validated against a **public oracle** (address,
   xpub, or known pubkey) — no device required.
3. Once a match is found, standard BIP-32/BIP-84 (or paper-wallet) derivation
   yields spendable keys; funds are swept on-chain.

Block notes the same `ngu.random` construction also feeds paper-wallet keys,
some ECDH material, XOR masks, and related features; severity varies by
feature. Multisig composed **only** of vulnerable COLDCARD-generated keys does
**not** remove the issue — a quorum of **secure** cosigners is required.

### Why review missed it (Coinkite)

Coinkite states both RNG implementations shared the same function signature; the
intended TRNG code was present in the binary, but end-to-end symbol resolution
from wallet seed generation was not verified. The `#ifndef` guard did not fail
the build when the macro was defined as zero. Hotfixes add build-time checks so
the wrong `rng_get` cannot link silently.

### Mitigations that actually work (per advisory)

- **Dice (≥50 independent private rolls)** mixed at seed creation on affected
  firmware (Coinkite exception).
- **Strong unique BIP-39 passphrase** (barrier, not a seed repair).
- **New seed on fixed firmware** + careful migration (test tx, verify
  fingerprints).
- Multisig with at least one cosigner whose key was **not** generated on the
  vulnerable path.

## Why it matters for Bitcoin history

Hardware wallets are marketed as the gold standard of **self-custody**. This
incident shows that:

1. **Integration bugs** across open-source submodules can silently collapse
   entropy for years.
2. Attackers need not steal devices if seeds are offline-enumerable.
3. Air-gapped signing does not help if the **seed was born weak**.
4. Firmware updates do not rewrite history for already-generated secrets.

### A recurring failure class, not a first

Weak random number generation has drained bitcoin wallets repeatedly for over
a decade. Commentators (including Jameson Lopp, who published a list of
affected projects as this incident unfolded) placed Coldcard in a long line of
precedents; the best-documented ones, each with its own primary disclosure,
include:

| Year | Incident | Failure | Primary disclosure |
| ---- | -------- | ------- | ------------------ |
| 2013 | Android `SecureRandom` | OS PRNG flaw; repeated ECDSA signing nonces exposed keys in Android wallet apps that generated or used keys on-device (Bitcoin Wallet/Schildbach, blockchain.info, BitcoinSpinner, Mycelium) | bitcoin.org network alert |
| 2011–2015 (disclosed 2023) | “Randstorm” / BitcoinJS `SecureRandom()` | JSBN fallback plus era browser `Math.random()` weaknesses degraded keys generated in web wallets of that period | Unciphered write-up |
| 2017–2023 (disclosed 2023) | Libbitcoin Explorer `bx seed` (“Milk Sad”, CVE-2023-39910) | Mersenne Twister seeded with 32 bits of system time → ~2^32 seed space; thefts observed July 2023 | Milk Sad team write-up |
| 2022 (disclosed 2023) | Trust Wallet browser extension (CVE-2023-31290) | MT19937 seeded with a 32-bit value → every generated wallet enumerable without user interaction | Ledger Donjon report |
| 2021–2026 | COLDCARD firmware (this case) | Build-flag mismatch silently bound seed generation to a deterministic software PRNG | Coinkite advisory; Block report |

The shared property is **offline exploitation**: the RNG failure is invisible
in normal use, the keys look valid, and no interaction with the victim is
needed at theft time. The recovery mechanics differ — Android's flaw leaked
keys through repeated ECDSA signing nonces, while Milk Sad, Trust Wallet, and
Coldcard left a reduced seed space that attackers could enumerate en masse,
often years later. Each episode
independently confirms the same lesson: entropy is a supply chain, and no
downstream cryptography can repair a seed that was born predictable.

## Reading notes

- This is **theft enabled by a vulnerability**, not a court case with a
  convicted defendant in the sources above.
- Do not equate “Coinkite bug” with “Coinkite stole funds.”
- Do not treat media dollar totals as fixed; they change as trackers update.
- Prefer Coinkite + Block over social-media chain analysis for technical facts.
- AI-assisted code audit is *hypothesized* by Coinkite as a discovery path for
  attackers; the root cause remains the deterministic RNG integration bug.
- The Lopp post is cited only as **commentary/aggregation** of prior weak-RNG
  incidents; every precedent in the table above is grounded in its own primary
  disclosure. Incidents from that list without an equivalent public write-up
  (e.g. several smaller wallet generators) are deliberately omitted here.
